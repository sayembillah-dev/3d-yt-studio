# StickWorld video — production state machine

You are running a production pipeline. **Numbers decide, not opinions.** Every phase ends at a gate that a script
checks. Never say "looks good": run the gate, paste the numbers, fix what fails, then move on.

## Paths (memorise) — always run commands from the studio root (the folder that holds CLAUDE.md)
```
ROOT=<the folder that contains CLAUDE.md>  # usually /Volumes/ssd/3D Youtube Studio, but the disk may mount under another name; cd there first. Every path below is relative to it and MUST be quoted (spaces)
S=Engine/scripts                          # all tools
R=Engine/references                       # style-bible.md, qa-rubric.md, fix-playbook.md, topic-rubric.md, reference_numbers.json, videos/
T=Engine/templates/project                # project skeleton (copied by new_project.py)
STUDIO=Engine/studio                      # Remotion + R3F engine (src/engine/*) + node_modules
P=Projects/<NN_slug>                      # the current video project (output/ holds the deliverables)
```
Engine imports inside a project: `@engine/...` (= Engine/studio/src/engine). render.sh selects the project for you.
Never use `npx` (the SSD is exFAT: no node_modules/.bin links); the scripts call node directly.
Examples to copy patterns from: `Engine/examples/00_gate` (gate shot, the canonical file split) and
`Engine/examples/demo-pirate-slice` (VO + captions).

## Step 0 — ALWAYS do this first (resume logic)
1. If the user names an existing project, or one is in progress: `cat $P/project.json` and read the phase in
   `"phase"`. If that phase is **Phase 6 (`shotplan`) through Phase 12 (`deliver`)**, do NOT run it here —
   hand it off to a subagent per "Working across sessions" below (it re-runs that phase's gate itself; state on
   disk may have changed). Phases 1–5 (`topic` through `voice`) run directly in this session.
2. If the user gives **timestamped feedback** ("at 0:12 the cat clips through the barrel"), hand it to the
   QA subagent (then re-run the finish group) the same way — see "Working across sessions" step 6 — instead of running the fix loop here.
3. Otherwise start at Phase 1 — and the **very first command** of a new video is
   `python3 $S/ledger.py begin` (starts the cost clock; before any question to the user).
4. After every phase passes, set `"phase"` in project.json to the next phase name **before** doing anything else
   (`python3 $S/new_project.py --set-phase $P <phase>`). This is what makes the work resumable after context loss.
   It also books the **cost ledger** (closes the old phase, opens the new one) — never change `phase` any other way.
   Re-entering a phase (timestamped feedback → `--set-phase $P qa`) is booked as a new row segment (= a fix loop).

### Cost ledger (MANDATORY for every video — user rule, 2026-11-06)
`<studio>/ledger.md` holds a table with **one row per video** and a column for every production metric: start/finish,
wall time, Claude-active time, sessions, models, API calls, tool calls, input / cache-write / cache-read / output tokens,
web searches, renders (count + minutes), fix loops, video length, est. API cost, paid extras, total cost, cost per
video-minute. It is generated by `$S/ledger.py` from Claude Code's session logs + `work/render_log.jsonl` (render.sh
writes it) — never edit ledger.md by hand. Rules:
- `ledger.py begin` first (Step 0.3); `new_project.py` and every `--set-phase` keep it current automatically.
- Every paid credit the user approved (ElevenLabs, stock music, …) → `python3 $S/ledger.py extra $P <usd> "<what>"`.
- Prices: `$R/pricing.json` (API-equivalent USD; update it when Anthropic's prices change — keep `as_of` honest).
- Per-phase breakdown: `python3 $S/ledger.py show $P`. Rewrite the table any time: `python3 $S/ledger.py refresh`.
- At delivery (Phase 12) paste the video's ledger row and the `show` breakdown to the user.

**Phase cards, not whole docs** (Improvements #11: in #01 each whole doc was re-read ~150×). Each phase reads its card
(< 1k tokens) — `$R/cards/script.md` (4–5), `cards/shotplan.md` (6–7), `cards/build.md` (8), `$R/qa-rubric.md` (9; it
IS the QA card), `cards/finish.md` (10–12). Open `style-bible.md` / `fix-playbook.md` only at the § a failed check or
the card names — read that section (Read with offset/limit or grep), never the whole file. style-bible stays the spec.
**Look-dev standard (user rule): style-bible §L + rubric S8.** Numbers passing is NOT enough — compare a still against
reference frames before any gate/QA is called done. New detail = engine defaults/props, never one-off project code.

## Working across sessions — subagent handoff (keeps this session's context small; saves ~$7/video)
Phases 1–5 (topic → research → format → script → voice) need the user's answers at each step: run them directly
in this session. From Phase 6 on, four phase groups are each self-contained — hand each to a fresh subagent
with the Agent tool instead of letting this session's context grow across all of them (that growth is most of
why video #01 cost 3× what it should have — see `Improvements/faster-and-cheaper.md`):

| Group | Phases | Card | Agent `model` / `effort` | Subagent does |
|---|---|---|---|---|
| shot plan → gate | 6–7 | cards/shotplan.md | `opus` / omit | shotlist.json, plan_lint, (if a new set/look) build + score the 00-style test shot |
| build | 8 | cards/build.md | `opus` / omit | scene code, cam_dump, cam_qa, batched stills, view the sheet |
| QA | 9 | qa-rubric.md | omit (inherit) / omit | render, qa_all, rubric review, fix loop |
| finish | 10–12 | cards/finish.md | `sonnet` / `low` | audio, thumbnail, metadata — scripted, gate-checked |

**Model per group (Improvements #10, user-approved 2026-11-06):** judgment phases (shot plan, look, build) run on
Opus at full effort; the scripted finish group runs on Sonnet at low effort (output is ~23 % of cost and ~73 % of it
was reasoning). Pass exactly the `model`/`effort` in the table — they are aliases, never version names. QA inherits
the session model. Re-running a gate with no code change (e.g. after the user answers a question) is also a
`sonnet`/`low` job.

How to hand off a group:
1. Before spawning: if `$P/work/handoff.md` isn't still the blank template, read it — it's the previous group's
   decisions and open issues. Confirm `project.json` `phase` is what you expect.
2. Spawn **one subagent at a time** — never two. Renders run at concurrency 3 (fastest measured) and the MacBook has 8 GB RAM and the exFAT
   SSD has already unmounted once under a write burst; a second render running at the same time would race it.
   Set `model`/`effort` from the table above (aliases only — never a version name).
3. Give it the full self-contained prompt below (it starts with none of this conversation's context).
4. When it reports back: open `project.json` yourself and confirm `phase` actually moved — never take the report's
   word for it ("numbers decide" applies to you too). Paste the gate output it reported **word-for-word** to the
   user; don't summarize it, don't reword it.
5. If it stopped with a question only the user can answer (a paid credit, a licensing choice, a fix loop that hit
   the 4-try limit) — ask the user yourself, then send the answer back to **that same subagent** with
   SendMessage (it still has the context; don't start a fresh one for this). The thumbnail frame is NOT one of
   these — Phase 11 already has the agent pick it.
6. Timestamped feedback ("at 0:12…") arriving after a group has shipped goes to the QA subagent (Phase 9 fix loop):
   SendMessage if it's still around, otherwise spawn a fresh one and hand it `work/handoff.md`. Then re-run the
   finish group (`sonnet`/`low`) so the mix, thumbnail and metadata match the fixed picture.

## Phase 1 — `topic`  (ask → score → choose)
1. Ask the user: **"What topic(s) do you have in mind? (or say 'suggest')"** — use AskUserQuestion when available.
2. For each candidate (theirs, or 5 you propose), score with `$R/topic-rubric.md` (6 criteria, /10).
   Show a table. Recommend the top one. Only topics ≥ 7.0 proceed; below that, propose a sharper angle.
3. Create the project: `python3 $S/new_project.py <slug> --title "<Working Title>"` → copies the template to `$P`,
   writes project.json `{phase: "research"}`. Slug = `NN_short-kebab` (NN = next free number in Projects/).
**Gate:** project.json exists, topic score ≥ 7.0 recorded in project.json `topic_score`.

## Phase 2 — `research`
1. Use WebSearch (standard mode; extended only for thin results). Find: the **strange action** (who did what odd thing),
   the **doubter** (who mocked it), the **mechanism** (why it actually works — concrete, drawable), 3–6 **specific
   numbers/names/dates**, and the **payoff** (what happened).
2. Write `$P/research.md`: facts as bullets, each with its source URL. Mark anything uncertain `UNVERIFIED` and do not
   use it in the script.
**Gate:** research.md has ≥ 5 sourced facts, a stated mechanism, and 0 UNVERIFIED facts used later.

## Phase 3 — `format`
Ask: **"Short (≈60 s, 9:16) or long-form (16:9)? Target duration?"** Defaults: Short, 59 s.
Write into project.json: `type` ("short"|"long"), `duration_s`, `words_target = round(duration_s × 3.66)`.
Long-form: run the whole pipeline per **chapter** (each chapter is one composition section of 45–90 s with its own
shot plan); gates are the same except duration and dissolves/min (compare `--skip duration`).

## Phase 4 — `script`
1. Write `$P/script.md` with the structure in `$R/cards/script.md` (style-bible §9; fill `$T/script.md` template):
   strange-action hook (line 1, ≤ 3 s, no question, no "Did you know") → doubter → "You see," pivot → escalation →
   quoted punch-line → **mechanism reveal in the last ~30 %** → abrupt payoff → last line loops into the first.
   Also the title (4–8 words, Title Case, "The [Object] That …" / "Why [Group] [Odd Thing]" / "Levels of …").
2. `python3 $S/script_lint.py $P/script.md --duration <duration_s>`
**Gate:** script_lint exits 0 (word count within ±8 % of duration × 3.66, hook rules, doubter, pivot, reveal position,
title rules, every sentence has a drawable noun). **Advisor checkpoint:** call `advisor()` once on the draft before
showing it to the user — structural problems (weak hook, buried reveal, no drawable mechanism) are cheap to fix now
and expensive once VO and a shot plan are built around them. Then show the script to the user and get approval
before Phase 5.

## Phase 5 — `voice`
1. Ask the user for the **voiceover mp3** recorded/generated from script.md (fast, bright, dry young voice; 3.66 w/s).
   Never clone a real person's voice. Save it as `$P/public/vo_raw.mp3`.
2. `python3 $S/tighten_vo.py $P/public/vo_raw.mp3 $P/public/vo.mp3 --script $P/script.md` — removes every gap > 0.30 s
   down to 0.12 s (cuts in silence only), reports wps before/after.
3. `python3 $S/transcribe.py $P/public/vo.mp3 $P/public/words.json --gate`
**Gate:** `TRANSCRIBE GATE: PASS` (exit 0). tighten_vo's wps is only an estimate from script words; transcribe's V1 is
measured exactly like the final compare (whisper words / word span, 3 decimals — never read a rounded 3.2 as a pass).
**WARN counts as not passed**: within 2 % of 3.2/4.1 the final mix (re-transcribed over music) can drift out —
#02 measured 3.198 here and 3.15 on the final, a hard fail at the last phase. Fix now, in this order: tighten_vo
`--keep 0.10`, denser wording (adding words at the same pace does not raise wps), `--atempo` ≤ 1.05 (the user found
1.10 rushed). Longest pause ≤ 0.33 s. Set `duration_s` in project.json = VO length + 0.5 s.

## Phase 6 — `shotplan`
1. Build `$P/shotlist.json` (template in `$T/shotlist.json`, worked example `$R/examples/shotlist_example.json`):
   one **beat** every ~1.7 s, aligned to words.json. For each beat: `id, from, to` (frames, 30 fps), `words`
   (the VO words in it), `sync` (the noun/verb that must be on screen at its word ±3 f), `set`, `visual`
   (what we see), `camera` (move kind: push/pull/whip/orbit/crane/pan/tilt/fly-through), `cast` (who, face, action —
   ONLY characters who will be ON SCREEN in that beat: cam_qa G18 checks it; an object-only beat has `cast: []`),
   `sfx` (list), `transition_in` ("flight"|"dissolve"|"cut").
2. Lay out the **sets** along one flight path (style-bible §4). 7–10 sets per 60 s. A set change is a flight through
   a portal (door, window, porthole, smoke) or an 8-frame dissolve mid-flight; ≤ 1 hard cut per Short.
3. `python3 $S/plan_lint.py $P`
**Gate:** plan_lint exits 0 (median beat 36–66 f, max ≤ 90 f, first change ≤ 45 f, 2 beats in 0–3 s, every beat has
a sync word that exists in words.json at that time, ≤ 1 cut, dissolves 8 f, every sentence starts a beat).
**Advisor checkpoint:** call `advisor()` once on the finished shot plan (set flow, beat spacing, sync words) before
moving to Phase 7/8 — a bad set layout or missed sync word is far cheaper to catch here than after a set is built.

## Phase 7 — `gate` (only when the project uses a NEW set or a new character look)
The guide's step that made the results good: **build ONE 3.6 s test shot (108 f) of the hardest set + 2 characters
before building the whole video**, and push it until it scores. Copy `Engine/examples/00_gate` as the pattern.
1. Build it (same files as Phase 8).
2. `bash $S/render.sh $P video <Comp>` then `bash $S/qa_all.sh $P gate <Comp>` — cam_qa + qa_frames + compare
   (with the gate skip list) in one call; one PASS/FAIL table, fix text only for what failed, full logs in
   `work/logs/`.
3. Score the 5 lenses in `$R/qa-rubric.md` using qa_frames' `work/qa/sheet_*.jpg` and `flag_*.jpg`.
**Gate:** every lens ≥ 7/10, compare.py 0 hard fails (`--skip voice,audio,duration,dissolves_per_min,median_beat_gap_s`), cam_qa all gates PASS.
(median_beat_gap_s is skipped only here: on a 3.6 s clip it is one gap; cam_qa G4–G7 + first_beat_s +
beats_in_first_3s still gate the pacing. Full videos never skip it.)
Record the scores in project.json `gate_scores`. Iterate fix → re-render → re-score (keep a log in `$P/work/gate_log.md`;
format: `Engine/examples/00_gate/work/gate_log.md`). **Advisor checkpoint:** before recording a PASS, call
`advisor()` once with the final render + lens scores — this gate's whole purpose is to lock in a look/set the rest
of the video gets built on, so it's worth the second opinion before committing to it.
Camera note: measured framing changes are motion PEAKS (mid-move), not waypoints — a move must be bold enough to
exceed the detector threshold (gentle drifts do not count as beats).

## Phase 8 — `build`
Read `$R/cards/build.md` and `$R/props-catalog.md` first: reuse catalog props; new reusable props go in
`props/<era-or-theme>.tsx` (header comment: theme + first video), then `node $S/props_catalog.mjs` (and `--check` in
the gate). Write the scene code. **Single source of truth per concern** (Sonnet: follow this split exactly):
| File | Contains | Checked by |
|---|---|---|
| `scenes/camera.ts` | `END`, `camera: CameraSpec` (waypoints, ease 'flow'), `TRANSITIONS` — multi-set videos: `CAMERAS` (one track per set, style-bible §L.2; pattern in Projects/01_dutch-water-line/scenes/plan.ts) | cam_qa.py |
| `scenes/blocking.ts` | `ACTORS` (pos or path per character), `OBSTACLES` (every solid prop), `at(id)`, `place(id)` | cam_qa.py G16/G17 |
| `scenes/cast.ts` | `CAST = defineCast({...})` (`@engine/cast`): per character `look` + `keys` (face/arms/fx/beat per frame) + `talk` | sfx_cues.mjs, qa |
| `scenes/sfx.ts` | `SFX_EXTRA`: hand cues for things not in keys (door, splash, coin) + `AMBIENCE` ranges | sfx_cues.mjs |
| `scenes/index.tsx` | sets + props + `<ToonCharacter {...CAST.x} {...place('x')}/>` + `<Captions/>` | render |
Rules (each is a QA check later):
- Characters: `ToonCharacter` only (3D toon, plum ink). Pose-to-pose: a key every 12–45 f per visible character,
  attacks are automatic (4 f bezier(.2,0,.1,1)), **no idle sway**; faces swap on the sync word.
- Every prop gets ink (`Inked` or a prop from `@engine/props/basic` — all inked). Every frame: foreground, midground,
  background, ≥ 2 ambient motions (motes, flags, gulls, water, smoke, lantern swing).
- Camera: waypoints at the beat frames from shotlist.json; all eases 'flow'; no key may brake (cam_qa G2).
- Captions: `<Captions words={words} />` (1–2 word chunks, cap height ≈ 42 px on the estimator).
Commands:
```
node $S/preflight.mjs $P           # ~2 s: PF1 types + PF2 rules of hooks (render.sh runs it before every render)
node $S/cam_dump.mjs $P            # camera + actors → work/camera_dump.json
# actor ids in blocking.ts = <shotlist cast id><n> (cast "watts" → watts12): G18 matches by that prefix, unmatched = FAIL
python3 $S/cam_qa.py $P            # G1-G19 (G18 cast on screen per beat, G19 heads not cut); FIX text per failure
bash $S/render.sh $P stills <Comp> 15,60,120,…   # one still per beat mid-frame → work/sheet_stills.jpg; LOOK at it
```
**Gate:** cam_qa all gates PASS (`CAM_QA: N/N`); `props_catalog.mjs --check` up to date; stills sheet viewed (Read the jpg) and every beat's `visual` from shotlist.json is visible.

## Phase 9 — `qa` (render → measure → review → fix loop)
Render speed (measured 2026-11-06, idle M1, #01's 58 s / 1746 f scene, incl. bundling): full size `video` 97–106 s ·
`preview` (270×480, full look, every QA number identical to full) 98–119 s · `pace` (pacing numbers only) 39–56 s ·
`splice` of 60 frames 49–56 s. The same full render took 7–15 min during #01 on a busy machine: before a render
round, keep heavy apps closed. Check `work/render_log.jsonl` `seconds` — if a full render takes > 5 min, switch the
fix loop to `preview` (≈ 2× faster on a slow machine) and render full size again only for the gate.
1. `bash $S/render.sh $P video <Comp>` → `$P/work/<Comp>.mp4` (silent, full size).
2. `bash $S/qa_all.sh $P qa <Comp>` → cam_qa + qa_frames + compare (audio skipped) in one call; one PASS/FAIL
   table, fix text only for what failed, full logs in `work/logs/`. qa_frames also writes `work/qa/`: auto
   findings (P0/P1 fail), flag strips, review sheets (one cell per 0.5 s, labelled with the spoken word + the
   shot beat), and a fresh `review.md` every run.
3. **Review**: Read the images listed in `work/qa/to_review.json` (qa_all prints `READ n/N sheets + m/M flags`).
   Round 1 lists all of them; fix-loop rounds list only sheets whose pictures/labels changed since the last round and
   only new flag strips (a camera.ts change re-lists everything; a splice lists its range). Unlisted images are
   pixel-identical to ones already reviewed: keep their verdicts in review.md. Before declaring the gate passed,
   run `qa_frames.py <P> <video> --all` only if review.md has an unchecked lens. Fill `work/qa/review.md` (the 5-lens
   rubric: each check yes/no with frame numbers). Score each lens /10 with the rubric's scoring rule.
4. **Fix loop**: for every failing gate/check look up `$R/fix-playbook.md` (keyed by the exact gate/check name), make
   the change, then re-check with the cheapest render that can show it:
   - pacing-only fix (beat gaps, first beat, holds, dissolves, cuts — camera.ts timing): `render.sh $P pace <Comp>` +
     `qa_all.sh $P pace <Comp>` (numbers only; its look is deliberately cheap — never judge the look from it).
   - fix confined to some frames (a prop, a pose, a collision): `render.sh $P splice <Comp> 300-420[,900-960]` —
     re-renders only those frames into `work/<Comp>.mp4` at its size (old one kept as `<Comp>.prev.mp4`), then
     `qa_all.sh $P qa <Comp>`. Pad each range ±15 f. A camera.ts change moves every later frame: not a splice.
   - anything else: `render.sh $P video <Comp>` again.
   Max 4 loops per issue; if still failing, stop and tell the user exactly what fails and why.
5. **Timestamped user feedback** enters here: convert each "m:ss" to a frame (× 30), render `range` ±30 f around it,
   view the strip, fix, re-render, show the user the before/after strip.
**Gate:** `qa_all.sh $P qa <Comp>` exits 0, every rubric lens ≥ 7, no open P0/P1. **Advisor checkpoint:** before
declaring this gate passed, call `advisor()` once with the final qa_all table + rubric scores — audio, thumbnail,
and delivery all build on this video being right, so a mistake caught here is far cheaper than one caught later.

## Phase 10 — `audio`
1. `node $S/sfx_cues.mjs $P` → `work/sfx_cues.json` (whoosh on every camera move > threshold and every dissolve, pop
   on every face swap, impact on every `beat`, hand cues from SFX_EXTRA, onomatopoeia from words.json).
2. `python3 $S/sfx_synth.py $P` → `work/sfx.wav` (procedural SFX; or ElevenLabs if `ELEVENLABS_API_KEY` is set and
   the user approved the spend).
3. Music: use `$P/public/music.mp3` if the user supplied one (must be licensed), else `sfx_synth.py --music` makes a
   procedural ~100 BPM plucky bed.
4. `bash $S/qa_all.sh $P final` → mix.py (`$P/output/final.mp4`: static music bed 20 dB under the voice, no
   ducking, ambience, SFX; mono; master −14 LUFS, TP −2 dBTP; voice −13.8 ± 1.5 dBFS RMS) + compare (now with
   audio + voice) in one call; one PASS/FAIL table, full logs in `work/logs/`.
**Gate:** `qa_all.sh $P final` exits 0 (MX1–MX4 PASS, compare 0 hard fails, size = full, never a preview); lufs −15…−13; TP ≤ −1.0.

## Phase 11 — `thumbnail`
`python3 $S/thumbnail.py $P --suggest` (top frames + `work/thumb_candidates.jpg`), then
`python3 $S/thumbnail.py $P --frame <F> --text "≤3 WORDS" [--zoom 1.2 --focus x,y]` → `$P/output/thumbnail.png`
(1080×1920 Short, 1280×720 long; re-rendered WITHOUT captions). Pick F = the most saturated, most emotional frame with
the hero object + main character (style-bible §9.3). **Gate:** TH1 PASS and Read `work/thumbnail_preview.jpg`:
hero object + face readable at the 10 % size.

## Phase 12 — `deliver`
Write `$P/output/metadata.md` (title, description 2 lines + sources from research.md, 3–5 hashtags). Tell the user the
paths: `output/final.mp4`, `output/thumbnail.png`, `output/metadata.md`, plus the final compare table and rubric scores.
Set phase `done` (`new_project.py --set-phase $P done` → closes the ledger), then paste the video's row from
`ledger.md` and `python3 $S/ledger.py show $P` (cost + time per phase) to the user.
